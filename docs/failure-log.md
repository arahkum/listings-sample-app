# Failure log: agent-implemented tickets review

3 tickets implemented directly from specs generated by Step 1's
`spec_generator` (see `specs/TICKET-*.json`), each on its own branch, with
tests, reviewed before merge. PRs: #1, #2, #3 (all merged, squashed).

## Patterns noticed across all 3 reviews

1. **Specs under-specify the response contract.** None of the 3 specs said
   anything about *response shape* (status codes, body structure) - only
   behavior ("returns 20 per page", "excluded from results"). TICKET-1 had to
   invent a `{items, total, page}` wrapper; a different implementer could
   reasonably have picked headers (`X-Total-Count`) instead. **Takeaway:**
   specs need an explicit "API contract" section, not just acceptance
   criteria, or every implementer (human or agent) will fill that gap
   differently and reviewers won't have a spec to check the choice against.

2. **"Edge case" wording gets implemented inconsistently unless the spec is
   precise about error vs. silent-correction semantics.** TICKET-1's spec
   said "defaults to 1" for invalid page numbers - I implemented a 422
   rejection instead (arguably better practice, but a literal spec
   violation). TICKET-2's "ignored, not an error" edge case *was* followed
   literally. Same reviewer (me), same session, two different fidelity
   choices depending on whether I thought the spec's choice was reasonable.
   An agent with less judgment might follow the letter of a bad spec, or
   silently "improve" on a good one - both need a human to actually read the
   diff against the spec, not just check tests pass.

3. **The highest-value review finding wasn't in the ticket text at all: a
   cross-ticket contract break.** TICKET-3's ticket text only described
   sold-listing visibility; implementing it *correctly* per that text meant
   changing `GET /listings`'s default (no-filter) behavior, which silently
   breaks the implicit "default search = active only" contract that
   TICKET-1 and TICKET-2 shipped. Tests all still pass (none of the earlier
   tickets' tests assert "no sold listings exist yet," so nothing failed) -
   this is exactly the kind of regression that a green test suite won't
   catch and a reviewer has to reason about by hand, because the ticket
   writer (and the agent) only had the current ticket's text in view, not
   the accumulated contract of everything shipped before it.

4. **Scope stayed clean when the spec was concrete (TICKET-2) and needed a
   judgment call when it wasn't (TICKET-1, TICKET-3).** No unrelated files
   touched in any of the 3 PRs - `AGENTS.md`'s "keep changes scoped" rule
   held up fine even without an agent enforcing it, because specs were
   narrow enough that there was no temptation to refactor nearby code.

## What this means for the rest of the pipeline

- Step 5's rule checks (schema valid, no empty fields) + LLM judge catch
  *generation*-time problems (did the LLM produce a usable spec?) but not
  *implementation*-time problems like #3 above - those only show up once code
  actually changes behavior across tickets. A real pipeline needs either a
  stronger spec template (explicit API contracts) or a human/agent step that
  diffs new behavior against previously shipped endpoints, not just the
  current ticket.
- Guardrails (Step 7) should include a diff-size/scope check, even though it
  wasn't needed here - it's cheap insurance against an agent run that *isn't*
  as disciplined as this one was.
